# Vault wallets (offline signing via HME Vault)

- EVM send routes resolve Vault balances only from the paired public address, never the random wrapping root; native and ERC-20 sends use restricted Vault intents and verify the complete signed transaction before broadcast. Why: displaying or signing for the wrapping anchor targets a different, empty wallet.
- Vault profiles are envelope `mode: "vault"` — random anchor like keyonly, no seed; watch-only account xpubs live in `pairing.ts` (scoped `hme.vault-link.v1`). Why: unlock/session/switch machinery stays byte-identical and no key material is ever stored.
- Vault profiles render the normal home screen (`wallet.index.tsx`): chain scans come from `vaultAccountSnapshot` (`snapshot.ts`) instead of the seed, and Send/Receive use `VaultBottomActions`, which builds unsigned PSBTs (`psbt-build.ts`) or `hm-evm-tx` intents (`evm-intent.ts`) shown as HMQR2 animated QRs (`qr-parts.ts` — must stay byte-compatible with HME Vault's `src/lib/signer/qr-parts.ts`); only signed hex comes back for verify + broadcast. `VaultHome` is only the unpaired fallback. Why: same experience up to signing, and the online wallet must never ask for an xprv.
- Wallet factory helpers (createVaultWallet etc.) only build the UnlockedWallet; saving is always saveWalletToNewProfile/saveWallet by the caller. Why: a factory that saves writes to the currently active profile slot and overwrites that wallet (this destroyed a seed envelope once).
